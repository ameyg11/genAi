6. The core SQL: How does vector similarity get calculated automatically?
This is the query you specifically asked about:
SELECT
    id,
    title,
    content,
    1 - (embedding <=> $1::vector)
        AS cosine_similarity
FROM documents
ORDER BY embedding <=> $1::vector
LIMIT 3;


To really understand it, we need to derive the math and then map the math to SQL.
6.1 What does cosine similarity mean?
Imagine we already have embeddings:
Document A = [1, 0]
Document B = [0.8, 0.6]
Document C = [0, 1]


And a user's query has the vector:
Query = [1, 0]


Treat the two numbers as coordinates of a direction in a two-dimensional plane.
- Document A points in exactly the same direction as the query.
- Document B points in a somewhat similar direction.
- Document C points in a different direction.
Cosine similarity calculates how closely the directions align.

Mathematically:
\[
\operatorname{cosineSimilarity}(A,B)
=
\frac{A\cdot B}
{\|A\|\|B\|}
\]

Here:
- \(A\cdot B\) is the dot product.
- \(\|A\|\) is the magnitude (length) of vector \(A\).
- \(\|B\|\) is the magnitude (length) of vector \(B\).
For the query and Document B:
\[
A=[1,0],\qquad B=[0.8,0.6]
\]

The dot product is:
\[
A\cdot B=(1)(0.8)+(0)(0.6)=0.8
\]

Both vectors have magnitude \(1\), so:
\[
\operatorname{cosineSimilarity}(A,B)=0.8
\]

The cosine distance is:
\[
\operatorname{cosineDistance}=1-0.8=0.2
\]

This is a miniature mathematical example—not an actual embedding generated by Gemini.
6.2 What is <=>?
pgvector defines the <=> operator as cosine distance.

For example:
SELECT
    embedding <=> '[1,0]'::vector
FROM documents;


It compares each stored vector with the given query vector.

The operator is not a special syntax built into JavaScript. PostgreSQL recognizes it because pgvector adds that operator to PostgreSQL's database functionality.

The extension contains the implementation needed to perform the vector calculation. When PostgreSQL executes the query, it invokes that implementation on compatible vector values.

Think of it like using a built-in SQL operator such as +, except this operator calculates cosine distance between two vector values.
6.3 What does $1::vector mean?
In Node.js, our query passes the query embedding as a parameter:
const queryVector = await embedText(
  query,
  "RETRIEVAL_QUERY"
);

const result = await pool.query(
  `
  SELECT id, title, content
  FROM documents
  ORDER BY embedding <=> $1::vector
  LIMIT 3
  `,
  [JSON.stringify(queryVector)]
);


Let's decode the SQL.

$1

This is a parameter placeholder. The first item in the array passed to pool.query supplies the value for $1.

::vector

This is PostgreSQL's cast syntax. It tells PostgreSQL to interpret the supplied textual vector representation as a pgvector vector.

embedding

This is the vector stored in the current database row.

Put them together:
embedding <=> $1::vector


means:
Calculate the cosine distance between this row's stored embedding and the query vector passed by the application.

The value is calculated for each candidate row considered by the query.

This is also why we use parameters rather than concatenating user input directly into SQL strings. Parameterized queries separate SQL structure from supplied values, which helps prevent SQL injection.
6.4 Why write 1 - (embedding <=> $1::vector)?
The operator calculates cosine distance. We often want to show cosine similarity instead.

The conversion is:
\[
\text{cosine similarity}
=1-\text{cosine distance}
\]

So:
1 - (embedding <=> $1::vector)
    AS cosine_similarity


does two things:
1. Calculates cosine distance.
2. Subtracts that result from 1, giving a cosine similarity score.
AS cosine_similarity names the calculated result in the query output. It does not create a permanent database column.

For normalized or arbitrary nonzero vectors under the cosine metric, cosine similarity ranges from \(-1\) to \(1\). It should not be interpreted as a probability that a retrieved document is correct.

6.5 Why does ORDER BY use distance rather than similarity?
The next line is:
ORDER BY embedding <=> $1::vector


By default, ORDER BY sorts in ascending order. That means the smallest distance appears first.

Imagine the calculated distances were:
Document	Cosine distance	Cosine similarity
A	0.00	1.00
B	0.20	0.80
C	1.00	0.00
Sorting by ascending distance places A, B, then C in that order.

We could instead write:
ORDER BY cosine_similarity DESC


in a query using the selected alias, but that form may prevent PostgreSQL from using a matching pgvector nearest-neighbor index. pgvector recommends ordering directly by the distance operator in ascending order and applying a LIMIT when performing indexed nearest-neighbor queries.

6.6 Why is LIMIT 3 needed?
LIMIT 3;


It means:
Return at most three rows after sorting the candidates by distance.

It controls the number of retrieved documents. It does not change the cosine-distance calculation itself.

So the whole query means:
1. Read candidate rows from documents.
2. Compare their vectors with the query vector.
3. Calculate a similarity score for display.
4. Sort by cosine distance, smallest first.
5. Return at most three rows.
That is how your SQL performs vector retrieval.

7. Exact search versus HNSW indexing
Now we can understand the index without treating it as magic.
7.1 What happens without an index?
Suppose the table contains one million document vectors.

When you run:
SELECT id, title
FROM documents
ORDER BY embedding <=> $1::vector
LIMIT 3;


PostgreSQL can perform exact nearest-neighbor search by comparing the query against all eligible vectors and identifying the nearest results.

Conceptually:
Query vector
   |
   +-- Compare with document 1
   +-- Compare with document 2
   +-- Compare with document 3
   +-- ...
   +-- Compare with document 1,000,000
   |
Sort distances
   |
Return top 3


This can be perfectly accurate for nearest-neighbor search under the specified distance metric, but the amount of work grows with the number of vectors.

For a tiny dataset, exact search is excellent because it is straightforward and provides a baseline for measuring correctness.
7.2 What is an index in general?
You already know that a regular database index can help find rows without scanning the whole table.

For example, a B-tree index on an email column helps PostgreSQL look up matching email addresses efficiently.

A vector index solves a different problem: finding vectors close to another vector under a particular distance metric.

For pgvector, one popular option is HNSW.

HNSW stands for Hierarchical Navigable Small World. It organizes vectors into a graph with multiple layers. Search navigates the graph to identify likely nearby vectors instead of comparing the query against every row.

Conceptually:
Exact search
Compare the query with all candidate vectors.
All eligible vectors

Exact nearest neighbors


Approximate search with HNSW
Navigate a graph to search likely neighbors faster.
Graph traversal

Usually faster, but may miss some true nearest neighbors


The trade-off is that HNSW can return results that differ from exact nearest-neighbor results. It generally aims for faster search while retaining high recall. It also needs memory and time to build the graph.

7.3 Create the HNSW index
Your SQL was:
CREATE INDEX documents_embedding_hnsw_idx
ON documents
USING hnsw (embedding vector_cosine_ops);


Let's go through each part.

CREATE INDEX documents_embedding_hnsw_idx

Creates a database index with this name.

ON documents

The index is built for the documents table.

USING hnsw

Selects HNSW as the index access method.

embedding

The index is constructed using the embedding column.

vector_cosine_ops

This is the operator class that tells the index to support cosine-distance ordering. It needs to match the distance operator used in your search query.

The statement doesn't embed any documents. It builds a structure that can make future similarity searches faster.
Why not build the index immediately?
Because you should first prove that:
- You can store valid embeddings.
- Your query creates a compatible vector.
- Your SQL returns sensible results.
- You understand how exact retrieval behaves.
Then you can compare indexed and unindexed search.

Also, a small table does not necessarily benefit from an HNSW index. The index has overhead, so PostgreSQL may reasonably choose an exact scan for a small collection.
What are the HNSW parameters?
When you need to tune HNSW, pgvector provides options such as:
CREATE INDEX documents_embedding_hnsw_idx
ON documents
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);


Parameter	Meaning
m	Maximum number of connections per graph layer
ef_construction	Candidate-list size used while constructing the graph
hnsw.ef_search	Candidate-list size used during a search
The defaults are a reasonable starting point. Increasing ef_construction can improve recall but increases index-building work and may reduce insertion speed. Increasing ef_search can improve recall but usually costs additional query time. 

GitHub




Use the default parameters until measurements demonstrate that tuning is necessary.

You can inspect what PostgreSQL plans to do with:
EXPLAIN ANALYZE
SELECT id, title
FROM documents
ORDER BY embedding <=> '[0.1,0.2,0.3]'::vector(768)
LIMIT 3;


That example query vector would need all 768 values to match a VECTOR(768) column. In your application, the parameterized query supplies the complete vector.

The important point is to inspect the actual query plan instead of assuming the index is being used.

9. How does the Docker container communicate with your backend?
This is a networking question. The most important thing is understanding where each process is running.

In our initial setup, only PostgreSQL is running in Docker. Your Node.js backend files are still on your computer.
Your computer

Project files: db.js, embed.js, seed.js, search.js

Node.js backend

Executes JavaScript, calls Gemini and uses the pg database driver.

TCP database connection

localhost:5432 on your computer

PostgreSQL Docker container

Runs the database server and pgvector. Executes SQL and stores rows and indexes.

Persistent volume: pgdata

Holds database files independently of the lifecycle of the container.


What does 5432:5432 mean?
ports:
  - "5432:5432"


The format is:
HOST_PORT:CONTAINER_PORT


So it maps port 5432 on your computer to port 5432 inside the database container.

This is why your Node.js backend can use:
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/vectordb


The backend connects to the host port, and Docker forwards that traffic to PostgreSQL inside the container.
Does the database container read db.js or search.js?
No. In this setup, those files run in the Node.js process on your computer. The database container does not directly access those files.

Your code calls the pg driver, and the driver communicates with PostgreSQL across the network. PostgreSQL receives SQL statements and parameter values, executes them, and returns results.

The pgdata volume is for the database's persistent files. It is not a folder containing your backend source code.

Docker Compose documents that host-to-container access typically uses the published host port, while communication between containers on the same Compose network uses their service names. 

Docker Docs



What changes if the backend is also put in Docker?
Suppose you later add a backend service:
services:
  backend:
    build: .
    environment:
      DATABASE_URL: postgresql://postgres:postgres@db:5432/vectordb
    depends_on:
      - db

  db:
    image: pgvector/pgvector:pg17
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: vectordb
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:


Here the backend and database are both containers in the same Compose network.

The backend uses:
db:5432


instead of:
localhost:5432


Why?

Inside the backend container, localhost refers to the backend container itself, not to the separate database container. Docker Compose makes the database reachable by the service name db.

If only your local machine needs to access PostgreSQL, you can publish the database port. If the backend is the only client, you can often omit publishing the port and communicate over the internal Compose network instead.

That is the difference between running your backend on your host machine and running it inside Docker.

10. Alternatives: Which choices should you know?
You do not need to memorize every alternative right now, but you should understand why they exist.
Decision	Main options	When to consider them
Vector storage	pgvector, Qdrant, Pinecone, Weaviate	pgvector when you want relational data and vectors together; a dedicated vector database when its features or operational model suit your scale and needs better
Search strategy	Exact nearest neighbors, HNSW, IVFFlat	Exact for small collections and correctness baselines; approximate indexes for larger datasets when speed matters
Similarity metric	Cosine distance, Euclidean distance, inner product	Choose according to the embedding model, normalization and retrieval behavior you need
Search method	Vector search, PostgreSQL full-text search, hybrid search	Hybrid search when semantic relevance and exact terms—such as product IDs or technical names—both matter
Vector representation	vector, halfvec, sparsevec, bit	Different storage, precision and indexing trade-offs
pgvector also supports other distance operators: <-> for Euclidean distance, <#> for negative inner product, and <+> for L1 distance. Its indexes are configured for particular distance operations, so you should not assume that an index built for cosine distance automatically accelerates every other metric.
